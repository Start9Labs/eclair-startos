# Eclair on StartOS

> Everything not listed in this document should behave the same as upstream
> Eclair. If a feature, setting, or behavior is not mentioned here, the
> upstream documentation is accurate and fully applicable — see the
> Documentation section of `instructions.md` for links.

[Eclair](https://github.com/ACINQ/eclair) is ACINQ's Scala implementation of the Lightning Network. It is a routing node with no wallet and no web interface of its own: it watches the chain through a Bitcoin Core node, funds its channels from a wallet in that node, and is driven entirely through a JSON API.

## Image and Container Runtime

The image is built from the `Dockerfile` in this repository rather than pulled from upstream. Upstream publishes `acinq/eclair` on Docker Hub, but that image is `x86_64` only and its versioned tags stopped in 2022; only `latest` is maintained. Eclair itself ships as a platform-independent JVM archive whose bundled native libraries — secp256k1, netty-epoll and jffi — each carry a `linux-aarch64` build, so the Dockerfile downloads the checksum-verified release archive onto `eclipse-temurin:21-jre-noble` and one artifact serves both architectures with nothing compiled.

| What          | Value                                                                |
| ------------- | -------------------------------------------------------------------- |
| Image source  | Custom `Dockerfile` — upstream release archive on a Temurin JRE base |
| Architectures | `x86_64`, `aarch64`                                                  |
| Entrypoint    | Custom: `eclair-node.sh` with the data directory pinned              |

The package runs a single subcontainer, `eclair-sub`, which holds the JVM process and is where `eclair-cli` lives. Attach to it with `start-cli package attach eclair -n eclair-sub`.

The archive's version and its SHA-256 are build arguments in the `Dockerfile`; the checksum is verified during the build, so a mismatched or truncated download fails the build rather than shipping.

## Volume and Data Layout

One volume holds everything Eclair writes. Eclair restricts its own data directory to `rwx------` on every start, because the seeds and the API password live there.

| Path                           | Contents                                                   |
| ------------------------------ | ---------------------------------------------------------- |
| `/data`                        | The `main` volume                                          |
| `/data/eclair.conf`            | Eclair's configuration, written by the package             |
| `/data/node_seed.dat`          | The node identity seed, generated by Eclair on first start |
| `/data/channel_seed.dat`       | The channel key seed, generated by Eclair on first start   |
| `/data/mainnet/eclair.sqlite`  | Channel state                                              |
| `/data/mainnet/network.sqlite` | The gossip graph                                           |
| `/data/mainnet/audit.sqlite`   | Payment and channel history                                |
| `/data/startos-store.json`     | StartOS-side state — currently only the JVM heap ceiling   |
| `/mnt/bitcoin`                 | Bitcoin's volume, mounted read-only for its RPC cookie     |

The seeds are the node's identity and are never regenerated. On-chain funds are **not** here — they live in a Bitcoin Core wallet (see [Dependencies](#dependencies)).

## File Models

The package owns `eclair.conf` outright and rewrites it on every start. It is written as JSON, which Eclair's HOCON parser accepts unchanged, so the file is both valid configuration and a typed model.

| Model        | File                       | Format                |
| ------------ | -------------------------- | --------------------- |
| `eclairConf` | `/data/eclair.conf`        | JSON (a HOCON subset) |
| `storeJson`  | `/data/startos-store.json` | JSON                  |

Three groups of keys behave differently, and the difference is what "why did my setting revert" comes down to:

- **Re-asserted on every start, hand edits do not survive.** `chain`, the API and peer bind addresses and ports, `bitcoind.auth`, `bitcoind.cookie`, `bitcoind.wallet`, and `blockchain-watchdog.sources`. Changing any of these by hand breaks the package's contract with StartOS or with Bitcoin, so the model forces them back.
- **Resolved from dependencies on every start.** `bitcoind.host`, `bitcoind.rpcport`, `bitcoind.zmqblock`, `bitcoind.zmqtx`, `socks5.*` and `server.public-ips`. These are addresses StartOS assigns; editing them by hand is pointless because the next start recomputes them. When Bitcoin is not installed the keys are omitted rather than filled with a placeholder.
- **Owned by the user through actions, and preserved.** Everything the Configuration actions expose — alias, color, routing fees, on-chain fee policy, channel limits — plus `api.password`. A hand edit to one of these survives, because the model only supplies a default when the key is absent or unparseable. Any key the model does not name is preserved verbatim, so an advanced setting added by hand stays put.

`startos-store.json` holds the JVM heap ceiling, which has no `eclair.conf` equivalent because it is a `java` argument rather than an Eclair setting.

## Dependencies

Eclair requires Bitcoin and cannot run without it. Bitcoin supplies the chain data Eclair watches, the fee estimates it uses, and the wallet its channels are funded from.

| Dependency | Required | Health checks awaited       | Mount                                      |
| ---------- | -------- | --------------------------- | ------------------------------------------ |
| `bitcoind` | Yes      | `bitcoind`, `sync-progress` | `main` volume at `/mnt/bitcoin`, read-only |

The mount exists so Eclair can read Bitcoin's RPC cookie; the package uses cookie authentication rather than an RPC user and password. Eclair reads the cookie once at startup, so the package restarts Eclair when Bitcoin writes a new one. An absent cookie is treated as Bitcoin being down rather than as the cookie being removed, which keeps Eclair from being restarted while its backend is already gone.

Bitcoin must be configured a particular way, and the package raises a task on Bitcoin to do it — see [Tasks](#tasks). The transaction index is a hard requirement rather than a recommendation: Eclair fetches transactions by id with no block hash, including one at startup that is not in any wallet, so a node without the index fails to start. The index in turn requires an unpruned node.

The package creates a Bitcoin Core wallet named `eclair` before starting the daemon, loading it if it exists and creating it with `load_on_startup` otherwise. A Bitcoin node with no wallet loaded is the default state, and Eclair refuses to start against one.

## Network Access and Interfaces

Two interfaces, neither of them a web interface — Eclair does not have one.

| Interface | Type  | Port | Protocol | Purpose                                                              |
| --------- | ----- | ---- | -------- | -------------------------------------------------------------------- |
| `api`     | `api` | 8080 | HTTP     | The JSON API, and the WebSocket at `/ws` that streams payment events |
| `peer`    | `p2p` | 9735 | Raw TCP  | Incoming connections from Lightning peers                            |

The API is the whole control surface: every client, dashboard and command line tool acts through it. It authenticates with HTTP Basic using an **empty username** and the API password.

Outbound Tor is configured through the `socks5` block whenever Tor's SOCKS proxy resolves, which is what lets Eclair dial `.onion` peers. Eclair's own `tor` block — which builds an onion service by driving Tor's control port — stays off, because the Tor package exposes no control port; the peer interface's onion address comes from StartOS instead and is announced through `server.public-ips`.

**An address is announced only when it is reachable on 9735.** Eclair appends `server.port` to every entry of `server.public-ips` and cannot express a per-address port — `NodeAddress.fromParts` reads a `host:port` string as a DNS name — so it can only announce addresses served on the port it listens on. The peer interface asks for external port 9735 and normally gets it, in which case every clearnet address qualifies and this rule does nothing. It bites only when a second Lightning service is installed and already holds 9735: StartOS then assigns eclair another external port, and its clearnet addresses are dropped rather than announced at an address that reaches the other service. Tor is unaffected — the onion's virtual port comes from the interface's preferred port, so it is always 9735. StartOS domains are excluded regardless: Eclair accepts at most one DNS hostname and refuses to start on a second.

## Installation and First-Run Flow

Install Bitcoin first, and let it finish syncing. Eclair asserts at startup that its backend is fully synchronized and aborts if it is not, so the package holds Eclair back until Bitcoin reports otherwise rather than letting it crash-loop; a service that sits in "starting" for a long time on a fresh Bitcoin install is doing exactly that.

Eclair will not start until the API password exists, which is what the critical task on install is for. Running that action is the whole of first-run setup: the seeds, the node identity and the Bitcoin wallet are all created without input.

The order the package enforces on every start is: ensure the Bitcoin wallet, wait for Bitcoin to be synced, then start Eclair.

## Actions

Every action is user-facing; the package declares no hidden actions. The Configuration group writes `eclair.conf`, which Eclair reads only at startup, so those changes take effect on the next restart.

**Set API Password** (`set-api-password`) — Run it once on install, and again whenever you want to revoke access. It rewrites `api.password` in `eclair.conf` and returns the new password, which is shown only then; nothing stores a recoverable copy. It is instant and safe to repeat, but each run invalidates the previous password, so every connected client has to be updated. Eclair reads the password at startup, so a rotation takes effect on the next restart. The action's name changes to "Rotate API Password" once one is set.

**Node Info** (`node-info`) — Reads the node's public key, alias, connectable URIs and processed block height from the running node. Read-only, instant, repeatable. Use it to get the URI a peer needs to open a channel with you; the URI list is empty until the peer interface has a public address.

**General Settings** (`general`) — Alias, color, whether new channels are announced, and trampoline relaying. Announcing is what makes your node routable by strangers; turning it off leaves existing announced channels announced. Instant, repeatable, applied on the next restart.

**Routing Fees** (`routing-fees`) — What you charge to forward payments, separately for announced and unannounced channels. Eclair applies a fee change to existing channels when it restarts. Instant, repeatable, applied on the next restart.

**On-Chain Fees** (`on-chain-fees`) — How fast funding and closing transactions should confirm, and the ceiling on the fee rate used to reclaim funds that are not at risk when a channel closes. That ceiling is the setting to raise when closing transactions are not confirming and you need the money back; Eclair re-bids the transaction at the new rate after a restart. Instant, repeatable, applied on the next restart.

**Channel Settings** (`channels`) — The smallest and largest channels the node will accept, how many payments may be in flight per direction, and what to do about coins left locked by an interrupted channel funding. The last of these is the one that matters during an incident: the default refuses to start until the coins are unlocked, and switching it to Unlock lets Eclair release them itself. Instant, repeatable, applied on the next restart.

**Performance** (`performance`) — The JVM heap ceiling. Raise it if Eclair stops with an out-of-memory error, which is the failure mode of a node that has grown more channels than the current ceiling supports. Instant, repeatable, applied on the next restart.

## Tasks

The package raises two tasks, one on itself and one on Bitcoin.

**Set the API password** — Raised on Eclair whenever `api.password` in `eclair.conf` is empty, which on a fresh install is immediately. Severity `critical`, so Eclair will not start and its ordinary controls are replaced by the prompt. Running **Set API Password** clears it. It returns only if the password is emptied by hand.

**Configure Bitcoin** — Raised on **Bitcoin**, not on Eclair, and it appears on Bitcoin's page with no indication of which package asked for it. It targets Bitcoin's own hidden `autoconfig` action and asks for ZeroMQ enabled, the transaction index enabled, and pruning off. Severity `critical`. Approving the pre-filled form on Bitcoin clears it; it returns whenever Bitcoin's configuration drifts away from those three values. On a pruned node, satisfying it means a full resync, because the transaction index cannot be built without one.

## Health Checks

Two checks: one on the Eclair daemon itself, and one that appears only while the node is unreachable from outside.

**Eclair** — Calls `getinfo` on the local API and reports the block height Eclair has processed. It reads "starting" rather than failing while the API refuses the call, because a JVM that is still loading and a node that is broken look identical from outside for the first minute or so.

A check stuck on "starting" for much longer than that is usually one of three things, in order of likelihood: Bitcoin is still syncing and the package is deliberately holding Eclair back; Bitcoin's wallet is disabled, so the wallet the package tries to create cannot be; or Eclair aborted at startup on one of its own assertions. The logs distinguish them — Eclair states its reason and exits rather than hanging.

**Node Reachability** — Declared only while `server.public-ips` is empty, and always reports `disabled` with an explanation. It is a prompt rather than a fault: a node with no external address still opens channels and routes payments, it just cannot be dialled, so nobody will open a channel with it.

Its message distinguishes the two ways to arrive there, because they look identical to the user and have different remedies. With no external address at all, it asks for one. Where the peer interface has a public address that could not be announced — a second Lightning service holds 9735, see [Network Access and Interfaces](#network-access-and-interfaces) — it says that instead and points at Tor, which is the only route that still works. Either way the check stops being declared once an announceable address exists.

## Backups and Restore

The strategy is a whole-volume copy of `main`. StartOS stops the service before copying, so the channel database is captured in a consistent state; unlike a running node, there is no need to fall back to the snapshot Eclair maintains for hot backups.

Excluded: `network.sqlite` and its write-ahead files, which hold the gossip graph Eclair re-downloads from its peers, and the log files. Everything else is captured, including both seeds, the channel database and the audit history.

A restored instance rebuilds the gossip graph on its own, which takes a while and makes payments fail to route until it is populated. It needs Bitcoin installed and synced before it will start.

**On-chain funds are not in this backup.** They live in the `eclair` wallet inside Bitcoin's data directory, and Bitcoin's own backup is what captures them. Restoring Eclair alone onto a server whose Bitcoin node does not carry that wallet brings back the channels without the coins that funded them.

## Limitations and Differences

1. **No web interface.** Eclair has never had one. The API is the only surface, and no dashboard on StartOS currently drives it.
2. **Mainnet only.** The chain is fixed; testnet, signet and regtest are not selectable.
3. **The blockchain watchdog is disabled.** Upstream polls bitcoinheaders.net, blockcypher.com, blockstream.info and mempool.space to detect an eclipsed Bitcoin node. The package sends that list empty, so nothing leaves the server uninvited, and that cross-check is not performed.
4. **Eclair does not manage its own on-chain keys.** Upstream supports holding the keys itself and giving Bitcoin a watch-only wallet. The package uses the ordinary arrangement instead, in which Bitcoin owns the keys — which is what makes the backup caveat above apply.
5. **SQLite only.** Upstream's PostgreSQL backend, and the `eclair-front` clustering it enables, are not packaged.
6. **Plugins are not supported.** There is no path for placing a plugin jar where Eclair would load it.
7. **Bitcoin must be unpruned and transaction-indexed**, which is a substantially larger disk commitment than a pruned node.

## Quick Reference for AI Consumers

```yaml
package_id: eclair
image: built from ./Dockerfile (eclipse-temurin base + upstream release archive)
architectures: [x86_64, aarch64]
subcontainers: [eclair-sub]
volumes:
  main: /data
file_models:
  - eclair.conf
  - startos-store.json
startos_managed_env_vars:
  - JAVA_OPTS
dependencies: [bitcoind]
interfaces:
  api: { type: api, port: 8080 }
  peer: { type: p2p, port: 9735 }
actions:
  - set-api-password
  - node-info
  - general
  - routing-fees
  - on-chain-fees
  - channels
  - performance
tasks:
  - { action: set-api-password, severity: critical }
  - { action: bitcoind/autoconfig, severity: critical }
health_checks:
  - eclair
  - reachability # declared only while the node has no external address
```
